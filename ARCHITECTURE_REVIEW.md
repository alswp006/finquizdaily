# Architecture Review
Generated: 2026-08-26T01:29:45.247Z

## Summary
The UI layer (components/, pages/) is clean and consistent — a well-documented set of composable pre-built primitives (Card, ScreenScaffold, SummaryHero, Amount/CountUp) with a single consistent SDK-guard idiom for Toss-native APIs. The lib/ layer is the weak point: it has three overlapping, mutually-inconsistent domain-type definitions (AppError, Question, ErrorCode) spread across types.ts, errorCatalog.ts, and contract.ts, plus two competing localStorage abstractions, which together create real risk of type confusion as the app grows.

## Issues
### Critical
- [duplication] Three different 'AppError' type shapes coexist: types.ts (code/message/statusCode?/timestamp?), errorCatalog.ts (code/httpStatus/userMessage/field?/context?), and contract.ts (code/message/httpStatus?/field?/timestamp). errors.ts has to manually translate between the errorCatalog shape and the types.ts shape (userMessage→message, httpStatus→statusCode) on every mapping call, and any file that imports the wrong 'AppError' will silently get incompatible fields. — Files: src/lib/types.ts, src/lib/errorCatalog.ts, src/lib/contract.ts, src/lib/errors.ts / Fix: Pick one canonical AppError shape (the errors.ts/types.ts one, since it's what's actually constructed at runtime), export it from a single module, and delete/mark contract.ts's declarations as historical spec text rather than TypeScript types consumers could accidentally import.
- [duplication] contract.ts declares a 'Question' type ({id,text,options,correct,explanation}) that is structurally different from the actual Question type used everywhere else ({id,category,text,choices,answerIndex,explanation,deepExplanation} in types.ts and questionBank.ts). A dev grepping for 'Question' and finding contract.ts first would implement against the wrong shape. — Files: src/lib/contract.ts, src/lib/types.ts, src/data/questionBank.ts / Fix: Remove the stale Question redeclaration from contract.ts (or clearly namespace/comment it as an outdated pre-implementation spec) and point readers to src/lib/types.ts as the single source of truth.

### Warnings
- [duplication] Two independent localStorage wrapper modules exist with overlapping responsibility and different resilience guarantees: storage.ts (getItem/setItem/removeItem — swallows all errors silently, no self-repair) and fqd-storage.ts (readArray/write/remove — namespaced keys, self-healing on malformed JSON with a console.warn). It's unclear which one new code should use. — Files: src/lib/storage.ts, src/lib/fqd-storage.ts / Fix: Consolidate to a single storage module (fqd-storage.ts's self-healing version looks more mature) and delete the other, or clearly document why both exist (e.g. generic vs namespaced) with storage.ts built on top of fqd-storage primitives instead of duplicating localStorage try/catch logic.
- [duplication] The 'SDK call may throw outside the Toss WebView, so wrap in try/catch and swallow' pattern for haptic feedback is copy-pasted verbatim in two components instead of being a shared helper. — Files: src/components/BottomCTA.tsx, src/components/FloatingTabBar.tsx / Fix: Extract a single `fireHaptic(type)` utility (e.g. src/lib/haptics.ts) used by both BottomCTA and FloatingTabBar.
- [naming] File naming convention within src/lib is inconsistent: most files use camelCase (apiFetch.ts, errorCatalog.ts, errors.ts, types.ts, utils.ts) but fqd-storage.ts uses kebab-case. — Files: src/lib/fqd-storage.ts, src/lib/apiFetch.ts, src/lib/errorCatalog.ts / Fix: Rename fqd-storage.ts to fqdStorage.ts (or storage.ts, after consolidating with the other storage module) to match the rest of src/lib.
- [dead_code] contract.ts declares many function-signature types (getDailyQuestionsFn, saveDailySessionFn, getProgressFn, recordScoreFn, addWrongAnswerFn, submitScoreFn, fetchLeaderboardFn, getTodayDateKeyFn, getWeekKeyFn, clampScoreFn) and data types (LeaderboardEntry, WrongAnswerNote, DailySessionState, UserProgress) referencing 'packets' (0001, 0003, 0007–0011) that have no corresponding implementation anywhere in the given source tree — no daily-session logic, rank API, notes/progress module, or date-key helpers exist yet. — Files: src/lib/contract.ts / Fix: Either implement the referenced packets, or if they're intentionally future work, keep contract.ts out of src/lib (move to a design-doc location) so it isn't counted as part of the active module graph and doesn't get flagged as dead/unused exports by tooling.

### Suggestions
- [duplication] Amount.tsx and CountUp.tsx duplicate the same wrapper: an inline-block span with whiteSpace:nowrap + tabular-nums, wrapping a Paragraph.Text with formatNumber(value)+unit. Only the animation logic differs. — Files: src/components/Amount.tsx, src/components/CountUp.tsx / Fix: Extract the shared nowrap/tabular-nums span + Paragraph.Text rendering into a small internal `NumericText` primitive that both Amount and CountUp compose, so the formatting rules (which are safety-critical per the comments about CJK line-break bugs) live in one place.
- [naming] contract.ts uses a distinct 'XxxFn' function-type suffix convention (getQuestionFn, apiFetchFn, submitScoreFn, etc.) that appears nowhere else in the codebase, where plain interfaces/types are used instead (Question, AppError, Result<T>). — Files: src/lib/contract.ts / Fix: If contract.ts is retained as living documentation, either align it with the codebase's actual type-naming style or clearly label it as a non-code spec artifact (e.g. move to docs/ and strip the .ts extension) so it isn't mistaken for importable types.
- [dead_code] utils.ts exports `cn` and `formatCurrency`, neither of which is referenced by any other file in the provided codebase (only formatNumber is used, by Amount.tsx and CountUp.tsx). — Files: src/lib/utils.ts / Fix: Confirm usage elsewhere in the full repo; if genuinely unused, remove them or wire them into the components that should be using them (e.g. cn for conditional className composition in AdSlot/TossRewardAd's plain className props).
- [structure] contract.ts is explicitly documented as an auto-generated, 'do not modify' cross-packet interface spec, yet it lives directly inside src/lib alongside real runtime modules and re-declares names (AppError, Question, ErrorCode) that collide with the actual implementations, creating import-ambiguity risk. — Files: src/lib/contract.ts / Fix: Move contract.ts out of src/lib into a non-source location (e.g. docs/contract.ts or spec/) so it can't be accidentally imported and its type names don't shadow/collide with the real ones.
- [consistency] The 'probe the SDK, swallow exceptions if unsupported outside the Toss WebView' pattern is re-implemented independently (slightly differently each time) in every native-SDK wrapper component rather than sharing one utility. — Files: src/components/AdSlot.tsx, src/components/TossPurchase.tsx, src/components/TossRewardAd.tsx / Fix: Extract a shared `safeSdkCall(fn, fallback)` / `isSdkSupported(probe)` helper in src/lib so all Toss SDK wrappers apply the WebView-guard consistently and the reasoning documented in AdSlot's comment isn't re-derived per component.
