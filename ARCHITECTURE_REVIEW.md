# Architecture Review
Generated: 2026-08-26T07:31:14.900Z

## Summary
The app itself (routes, pages, storage utilities, date helpers) is small, consistently named (camelCase throughout), and free of circular imports, but it carries a second, disconnected layer of code: a contract.ts 'interface spec' and a useDailyQuiz hook whose declared shapes don't match what the pages actually do, plus a storage.ts history/ranking API that pages quietly bypass in favor of duplicated ad-hoc logic. This drift between the intended architecture (per contract.ts) and the implemented one is the codebase's main structural risk.

## Issues
### Critical

- [dead_code] useDailyQuiz.ts exports a hook that no page imports; every page (QuizPage, ResultPage, WrongNotePage) instead calls loadQuestions()/loadQuizState() directly from lib/quizState.ts, duplicating the validation/selection logic the hook was meant to centralize. — Files: src/hooks/useDailyQuiz.ts, src/pages/QuizPage.tsx, src/pages/ResultPage.tsx, src/pages/WrongNotePage.tsx / Fix: Either wire all pages through useDailyQuiz for question loading, or delete the unused hook if the direct-loadQuestions pattern is the intended approach.

- [duplication] The accuracy percentage formula (correctCount / total * 100, rounded) is implemented twice: once as the shared calculateAccuracy() in quizState.ts, and again inline inside storage.ts's getRankingData. — Files: src/lib/quizState.ts, src/lib/storage.ts / Fix: Have getRankingData call calculateAccuracy(history) instead of recomputing the ratio inline.

### Suggestions
- [consistency] Data-loading pattern is inconsistent across pages: RankingPage treats its data source as async (useEffect + isLoading state + fetch fallback) while QuizPage/ResultPage/WrongNotePage read localStorage synchronously during render with no loading state, even though all four ultimately read local data today. — Files: src/pages/RankingPage.tsx, src/pages/QuizPage.tsx, src/pages/ResultPage.tsx, src/pages/WrongNotePage.tsx / Fix: Standardize on one data-access pattern (e.g. a shared hook returning {data, isLoading}) used uniformly across all pages, regardless of whether the backing source is currently sync or async.
- [dead_code] RankingPage's remote-fetch branch (fetch(RANKING_API_URL)...) is unreachable in practice since RANKING_API_URL is hardcoded to an empty string, meaning that code path never executes and only adds maintenance surface. — Files: src/pages/RankingPage.tsx / Fix: Remove the dead fetch branch until a real ranking API endpoint exists, or gate it behind a feature flag with a clear TODO.
- [structure] Two overlapping type-definition files exist (types.ts as the stated canonical domain types, contract.ts as a generated 'interface contract') with conflicting entities for the same concepts (Question vs Quiz, QuizState vs QuizAnswerState), and lib/storage.ts imports from both, blurring which file is actually authoritative at runtime. — Files: src/lib/types.ts, src/lib/contract.ts, src/lib/storage.ts / Fix: Merge into a single source of truth for domain types (types.ts), and keep contract.ts (if retained at all) purely as non-imported documentation, not something production modules type-import from.
- [naming] contract.ts uses a 'Fn' suffix naming convention for type aliases (loadDailyQuizFn, useDailyQuizFn, calculateAccuracyFn, isQuizAvailableFn) that appears nowhere else in the codebase's actual implementations, which use plain verbNoun function names without the suffix. — Files: src/lib/contract.ts / Fix: Drop the Fn suffix convention or, if kept for contract files specifically, document it as a project-wide convention so it doesn't read as a one-off inconsistency.
